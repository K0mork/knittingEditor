# 2026-11-24 — CIのXcodeを27.2に上げる

- 影響: PRのCIの`ios`ジョブと、`Full iOS validation`の`ios_full`・`app_update`・`release_archive`ジョブを、`macos-26`イメージのXcode 26.6から、2026-11-23にGAになった`xcode-27`イメージのXcode 27.2（27B52）へ移した。提出用のアーカイブを作る手元のXcodeと同じ版になり、CIで確かめるビルドと提出するビルドのSDK（iOS 27.2）が揃う。テストはiOS 27.2のSimulatorで動く。イメージにはiPhone SE (3rd generation)の端末が無いため、これまでどおり`boot-simulator.sh`がiOS 27.2のランタイムで作る。iPhone DuoのSimulatorはCIで使わない（利用者の決定。開閉をsimctlで切り替えられず、CIでは既定の姿勢しか試せないため）。アプリの動作は変わらない。
- 主なファイル: `.github/workflows/ci.yml`、`.github/workflows/ios-full.yml`、`ios/UITests/KnittingEditorUITests/KnittingEditorUITests.swift`、`ios/docs/APP_STORE_CHECKLIST.md`、`ios/docs/RELEASE_RUNBOOK.md`、`ios/design/app-icon/README.md`
- 文書: CIのXcodeが26.6であることを理由にしていた記述を直した。提出用のアーカイブを手元で作る理由は、CIのアーカイブが署名なしであることにした。アイコンでIcon Composer 2.0の項目を使わないという制約は、CIのXcode 26.6で読めるようにするためのものだったので消した。
- CI: 新しいイメージでは、UIテストが全体に1.2〜2.5倍遅かった（PRの`ios`ジョブの同じテストを、Xcode 26.6の直近の成功と比べた）。そのため、テストごとの上限の最大（`-maximum-test-execution-time-allowance`）を240秒から360秒に、`ios_full`のジョブの上限を60分から75分に上げた（利用者の決定）。iPadの`ios_full`は、変更前の上限で58.6分かかった。さらに、ファイル選択画面を使う`testBackupExportSheetDismissesBackToEditor`（これまで41〜70秒）が、iPhone SEで選択画面の要素を探す1回に13〜31秒かかり、既定の上限150秒を超えた。選択画面を使うテストは同じように遅くなりうるため、既定の上限（`-default-test-execution-time-allowance`）も150秒から300秒に上げた。既定より長くするためにテストの中で240秒・300秒を指定していた9件は、既定以下になるので360秒にした。そのうち`testGuideNavigationReturnsToUsableEditor`（これまで110秒前後）は、PRの`ios`ジョブで要素を探す1回に10〜31秒かかり、240秒を超えていた。
- テスト:
  - `testGuideExternalLinkShowsNoPreview`と`testNarrowToolbarKeepsLongStitchAndPasteBandUsable`は、起動直後に「使い方」・「編み目記号を選ぶ」を押すが、準備中の表示（`editorLoadingOverlay`）が消えるのを待っていなかった。新しいイメージでは、どちらも押しても画面が変わらず、前者はiPhone 17とiPadで2回ずつ、後者はiPhone 17で2回失敗した。手元のiOS 27.2では、変更前のテストでも通った。前者は表示が消えるのを待ってから、ほかの使い方のテストと同じ`openGuide(with:in:)`で開くようにした。後者は、表示が消えてから押し、10秒たってもパネルが開かなければ1回だけ押し直す`tapAfterEditorLoads`を通す。押し直したときは、`openDocumentsPanel`と同じく経過を`TAPRETRY`としてジョブログとxcresultに残す（#441の調査に使う）。
  - `testAccessibilityExtraExtraExtraLargeKeepsPrimaryControlsUsable`（自分の上限240秒）と`testRestorePickerDismissesBackToEditor`（既定の150秒）は、新しいイメージで上限を超えた。どちらもテストの上限を360秒にした。後者は、ファイル選択画面の要素を探す1回が、Xcode 26.6の0.3〜0.6秒に対して10〜35秒かかっていた。手元のiOS 27.2では3回とも通った（70・35・35秒）。
- 検証:
  - `ruby -ryaml -e 'YAML.load_file(...)'`で、`ci.yml`と`ios-full.yml`がどちらも読めた。
  - `sh ios/scripts/check-app-store-docs.sh`が`App Store documents are structurally valid`で成功した。
  - `vitest run scripts/app-privacy-docs.test.mjs scripts/playwright-artifacts.test.mjs scripts/ios-full-failure.test.mjs`（変えたワークフローと文書を読むテスト）が49件成功した。worktreeに`node_modules`が無いので、同じlockfileのmainのcheckoutの`node_modules`で実行した。
  - `node scripts/check-pr-smoke-ui-tests.mjs`が`PR smoke UI test list: 11 existing tests`、`Device UI test list: 14 existing tests`で成功した。`vitest run scripts/ios-full-failure.test.mjs scripts/playwright-artifacts.test.mjs scripts/check-pr-smoke-ui-tests.test.mjs`が42件成功した。
  - 手元のXcode 27.2で、iOS 27.2のiPhone 17のSimulator（KE verify iPhone）に、直した4件（上の2件と上限を変えた2件）を`xcodebuild test -only-testing:...`で流し、すべて成功した（AX5 92秒、使い方の外部リンク 84秒、狭いツールバー 37秒、復元の選択画面 23秒）。押し直し（`TAPRETRY`）は起きなかった。
  - `git diff --check`が成功した。
  - `actionlint`は入っておらず、実行していない。
  - 手元で実行していないこと: `npm test`（全体）、`npm run build`、`npm run check:dist`、`npm run test:e2e`（Webのソースと依存は変えていない。PRのCIの`web`ジョブで確かめる）。
  - 変更前のコミット（`38fbaae`）をこのブランチで手動実行した`Full iOS validation`（run 45399425116）では、どのジョブも`xcodebuild -version`がXcode 27.2（27B52）、イメージが`xcode-27-arm64`だった。`app_update`（両端末とも`ios-v1.2-build1`から）、`release_archive`、`ios_full (iPhone SE (3rd generation))`は成功した。`ios_full (iPhone 17)`と`ios_full (iPad (A16))`は、上に書いたテストで失敗した。同じコミットのPRのCIの`ios`ジョブでは、`testRestorePickerDismissesBackToEditor`が時間切れで失敗した（ジョブは次のpushで取り消された）。
  - 上の待ち方の修正と360秒への引き上げを入れた`953c26b`の`Full iOS validation`（run 45411261329）では、`ios_full (iPad (A16))`、`app_update`の2つ、`release_archive`が成功した。`ios_full (iPhone 17)`は`testAccessibilityExtraLargeKeepsPrimaryControlsUsable`と`testBlockSaveAndFullBackupRestoreFollowGuide`がテスト自身の上限240秒を、`ios_full (iPhone SE (3rd generation))`は`testBackupExportSheetDismissesBackToEditor`が既定の上限を超えて失敗した。同じコミットのPRのCIの`ios`ジョブは、`testGuideNavigationReturnsToUsableEditor`が240秒を超えて失敗した。これを受けて、既定の上限と9件の上限を上げた（上のCIの項）。
  - `b975e76`のPRのCI（run 45422968264）は、`ci-gate`まですべて成功した（`ios`ジョブは28分）。同じコミットの`Full iOS validation`（run 45425690419）は、どのジョブもXcode 27.2（27B52）で動き、`ios_full (iPhone 17)`（55分）、`ios_full (iPad (A16))`（53分）、`app_update`の2つ（両端末とも`ios-v1.2-build1`から）、`release_archive`が成功した。`ios_full (iPhone SE (3rd generation))`は、テストの途中でランナーがGitHubとの通信を失って止まり（`The hosted runner lost communication with the server`、ログは残らなかった）、失敗したジョブを再実行した。再実行では、iOS 27.2のランタイムで作ったiPhone SE (3rd generation)のSimulatorで、14件が再試行なしで通り（小さいiPhoneでは試さない文字サイズAX5の2件はスキップ）、28分で成功した。
- デプロイ影響: `.github/workflows/`の変更なので、マージ後にPagesへ配信し直されるが、Webのソースは変えていないので配信物の中身は変わらない。配信後は`smoke`の成功と、マージ後の`Full iOS validation`の全ジョブの成功を確かめる。TestFlightと提出物は変わらない。
