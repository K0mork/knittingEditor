# Web版の製品計測

## 目的と範囲

試し操作、制作の進行、別日の継続制作、編集後の出力を区別し、改善の判断材料とする。対象はWeb本番版の編集画面だけである。送信実装は`src/analytics.ts`、イベントの呼び出し元は`packages/editor-core/ui/useEditorController.ts`、制作量の判定は`packages/editor-core/chartProgress.ts`に置く。iOS版は`NO_ANALYTICS`を使い、イベントを送らず、計測用の端末内状態も持たない。

開発ビルド、`navigator.webdriver`が有効な自動テスト、User-Agentに`Claude/`を含むアプリ内ブラウザ、オプトアウト中は計測を動かさず、計測キーを読み書きしない。オプトアウトの場合だけは既存の計測キーを可能な範囲で削除する。一般のアプリ内ブラウザすべてを除外するわけではない。

## 定義と編集の扱い

作成量は、追跡開始時の記号ありマス数`baseOccupied`に対する純増`net = max(0, board.occupiedStitchCount - baseOccupied)`である。到達判定には過去最大`maxNet`を使う。同じマスを描いて消す反復やUndoで作成量を加算しない。一度到達した閾値はUndoや消去で取り消さない。現在残っているマス数や総操作回数そのものではない。

操作量の参考値`touched`は、確定した編集で値が変わった異なるマス数を数える。同じページセッション・編み図・ローカル日内ではメモリ上のビットマップで重複排除し、保存するのは数だけである。編み図切り替え、サイズ変更、日付変更でビットマップをリセットする。再読み込みや再訪、複数タブでは同じマスを再び数えうるため、厳密なユニークマス数ではなく上限側の参考値である。閾値には使わない。

| 操作 | 作成量 | 編集日・操作時間・操作量 |
|---|---|---|
| 描画・消去・線、貼り付け | 実際に変化し履歴に確定した状態で`net/maxNet`更新 | 前向きの編集として記録。値が変わったマスを`touched`へ加える |
| サイズ・構造変更、背景色変更、その他の`changed()` | 状態が変わった場合だけ更新 | 前向きの編集。背景色変更だけではマスの値は変わらない |
| Undo/Redo | `net/maxNet`のみ更新 | 新しい編集日、操作時間、`touched`を加えない |
| 記号・色の選択、パネルを開く、無変更操作 | 加算しない | 加算しない。履歴の`record`が`false`なら編集にしない |
| `.knit`インポート／復元、複製、導入前の編み図 | 初めて追跡した状態を基準にする | 既存の内容を過去の制作量として遡及計上しない。復元は新しいIDで、複製と同様に別の追跡になる |

操作時間`activeMs`は編集活動（描画途中の実際の変更を含む）ごとに、直前の活動から60秒以内ならその間隔を加える。60秒を越える間隔は加えず、毎回直前時刻を更新する。ページ非表示・編み図切り替え時に直前時刻を消す。開きっぱなしやバックグラウンドの時間、実作業時間全体を表すものではない。確定前の描画活動だけでは編集日や到達イベントを増やさない。

編集日は端末のローカル暦日`YYYY-MM-DD`で、前向きの編集があった異なる日数を`editDays`、直近の日を`lastEditDay`とする。日差は経過ミリ秒の24時間割りではなく暦日差である。日付をまたぐ描画は確定時の日を編集日とする。端末時計・タイムゾーン変更の影響を受け、GA4のプロパティのタイムゾーンによる日付とは一致しない場合がある。

### 出力状態と出力イベントの意味

出力要求時に行・列・セル・ガイド線・背景色の32bit FNV-1aハッシュを一度計算する。16進ハッシュは端末内でのみ比較し、送信しない。名前・ファイル名は比較に含めない。到達済み閾値・到達日と要求日時もその時点で固定する。保存・共有の完了待ち中に到達した閾値は、その出力に結び付けない。出力までの暦日差は要求日から計算し、同じタブ内の出力要求時刻は同一ミリ秒でも単調増加させ、古い出力が遅れて完了しても新しい出力のハッシュを上書きしない。

1. 追跡開始時の`baseHash`と同じなら`unedited`。
2. それ以外で`lastExportHash`と同じなら`same_state`。
3. それ以外で過去の出力がなければ`edited_first`。
4. それ以外なら`edited_since_export`。

`chart_exported`はPNG/PDF生成が終わり、ブラウザへ保存・共有を求めた段階を示す。端末への保存完了や作品の完成を意味しない。プラットフォームが取りやめを報告した場合（`saved`が`false`）もこのイベントは送るが、`lastExportHash`を更新せず、`chart_progress_exported`を送らない。結果が不明な通常のダウンロードは要求時点を記録する。ハッシュは暗号学的な同一性証明ではなく、衝突による誤分類がありうる。

## 端末内の状態と限界

`localStorage`の`knitting-editor:chart-progress:v1`へJSONの`{ v: 1, charts: { [documentId]: ChartProgressRecord } }`を保存する。ドキュメントIDはこの端末内の対応付けにだけ使う。各記録は基準の記号数・ハッシュ・由来、`maxNet`、閾値ごとの到達日`reached`、出力済み閾値`exportedThresholds`、編集日数と直近編集日、操作時間と操作量、直近出力のハッシュ・時刻、更新時刻を保持する。継続イベントの日の重複排除も端末内で行う。座標ビットマップと直前の活動時刻はメモリにだけ置く。

最大200件で、更新が古い編み図から除く。編み図削除時はその計測記録も削除する。壊れたJSONはこのキーだけを破棄し、編み図のIndexedDBには触らない。計測の保存・JSON・送信の例外は捕捉し、編集・保存・出力を止めない。保存領域が使えないときはタブ内のメモリで重複排除し、編み図を開き直しても未保存の状態を保持する。保存済みだった記録が別タブの削除や上限除外で消えた場合、そのタブの古いキャッシュは破棄し、flushで自動的に再挿入しない。明示的にその編み図を再び開くと、現在の盤面を新しい基準として追跡を再開する。

再読み込み後は記録を引き継ぐ。各flushでは保存済みの最新値を読み直し、`maxNet`は最大、到達閾値は和集合（到達日は最も早い日）、出力済み閾値は和集合とする。直近編集日は後の日、編集日数はその記録の値（同日なら最大）、基準は最初の書き込みを採用する。操作時間・操作量は保存済み値に当該タブの未保存差分だけを加える。直近出力ハッシュは出力要求時刻の遅い記録を採用する。

一度だけのイベントは送信直前にも最新ストレージを読み、未記録であることを確認し、記録・保存してから送る。別タブで記録済みなら送らない。ただし`localStorage`の読み書き全体に原子的ロックはないため、完全に同時の別タブ処理の重複排除は保証できない。編集日数も並行編集の完全な集合ではない。通信失敗後の再送は保証せず、記録後に通信が失敗すれば欠測しうる。

端末・ブラウザをまたぐと別の編み図として数える。保存領域消去、上限による除外後の再訪では、その時点の基準からやり直す。復元・複製も別の編み図である。復元・複製は初めて開く前の登録時に由来と基準を保存する。削除・上限除外を検知したタブでも、明示的に開き直すと再読み込みなしで新たな基準から追跡する。過去の制作履歴は復元できない。

## 指標の読み方

閾値は`PROGRESS_THRESHOLDS = [20, 100, 500, 2000]`という仮説であり、「本格利用」の定義ではない。

閾値T・到達週Wについて、分母は`chart_progress`の`progress_threshold=T`かつ`cohort_week=W`のイベント数、分子は`chart_progress_exported`の同じT・Wかつ選んだ`export_lag_bucket`のイベント数である。7日窓なら`0`と`1-6`を合計する。到達後の同一状態または後続状態の出力を数えるが、基準状態に戻した`unedited`出力は含めない。

到達週の終了から観測データ末尾までに少なくとも窓の長さがある週だけを評価する。それより新しい週は「観測不足」とし、分母・分子からそろえて除く。期間の開始側でも到達イベントが欠けないようにする。保持期限外の到達週は評価しない。任意の日数窓を細かい区分の途中で切ることはできない。

これは1端末内の編み図ごと・閾値ごとの件数であり、利用者数ではない。閾値間には同じ編み図が重複するので合計を総編み図数としない。利用者単位の編集率・出力率とは別の表にする。出力しなくても制作・利用できるため、出力率だけを成功基準にしない。到達閾値の分布、`chart_resumed`の別日継続と間隔、編集日・操作時間・操作量の区分を並べて見る。

区分から正確なマス数の平均・合計、正確な制作時間、正確な平均出力日数は算出できない。端末をまたぐ同一編み図の追跡、作品の完成率、端末への保存成功率、導入前の制作量も求められない。

## GA4の設定と閲覧

この文書は設定・確認手順であり、実プロパティの設定完了や実受信の確認記録ではない。公開文書にはプロパティID、ダッシュボードURL、実測値やスクリーンショットを書かない。

### カスタム定義・保持期間

管理の「データの表示」→「カスタム定義」で、以下をそれぞれイベント範囲のカスタムディメンションとして登録する。イベントパラメータには同じ綴りを指定する。

`progress_threshold`, `progress_bucket`, `export_state`, `chart_origin`, `edit_days_bucket`, `gap_days_bucket`, `active_minutes_bucket`, `touched_cells_bucket`, `cohort_week`, `export_lag_bucket`

いずれも少数の区分で、編み図IDのような高カーディナリティ値ではない。`cohort_week`だけは週ごとに種類が増えるが、個々の編み図を区別しない。既存の`export_format`, `board_size_bucket`などで内訳を見る場合は既存定義を確認し、不足分だけイベント範囲で登録する。編み図ID・名前・ハッシュを送信したり登録したりしない。登録後、レポートで使えるまで待ち、登録前のデータを遡及して補えると考えない。[公式のカスタム定義の説明](https://support.google.com/analytics/answer/14240153?hl=ja)

管理の「データの収集と修正」→「データの保持」でイベントデータの保持期間は14か月を推奨する。これは設定変更の推奨であり、変更済みの主張ではない。探索で参照できるイベント単位データの期間に影響し、標準の集計レポートとは扱いが異なる。[公式の保持期間の説明](https://support.google.com/analytics/answer/7667196?hl=ja)

### 探索（自由形式）での再現

1. 「探索」→「自由形式」を作り、到達週の開始から、評価する出力窓を含む観測末尾までを期間にする。保持期間内で、処理が落ち着いた日までを選ぶ。
2. ディメンションに「イベント名」、上記10項目、必要なら`export_format`を取り込む。指標に「イベント数」を取り込む。「総ユーザー数」を分母にしない。
3. 分母のタブで行を`cohort_week`と`progress_threshold`、値を「イベント数」にし、イベント名が`chart_progress`と完全一致するフィルタを付ける。評価するT・Wを限定し、観測不足の週を除く。
4. タブを複製して分子用にし、イベント名を`chart_progress_exported`へ変更する。T・Wは同じにし、7日窓なら`export_lag_bucket`を正規表現`^(0|1-6)$`で絞る。形式別なら列に`export_format`を追加するが、全形式の合計を分子とする。
5. 同じT・Wの分子を分母で割る。分母0、欠測、しきい値適用時は算出不能として区別する。必要な計算・書き出しは非公開領域で行い、実数値を公開リポジトリへ置かない。
6. 別タブで`chart_progress`の閾値分布、`chart_resumed`の`gap_days_bucket`・`edit_days_bucket`を並べる。到達時点の時間・操作量区分も確認する。利用者単位の評価は別にする。

GA4の日付はプロパティ基準、`cohort_week`と日差は端末基準なので、期間端の境界を含む余裕を持たせる。データ品質アイコンでしきい値・サンプリング等を確認し、隠れた行を0としない。反映遅延や送信遮断による欠測もある。探索の手順が作れることと、実データで妥当な集計を確認したことは区別する。[公式の探索の説明](https://support.google.com/analytics/answer/7579450?hl=ja)、[公式のデータ更新頻度](https://support.google.com/analytics/answer/11198161?hl=ja)、[公式のデータのしきい値](https://support.google.com/analytics/answer/9383630?hl=ja)

### 受信の確認

通常の運営者検証は次節の除外を維持する。実受信の検証だけは、承認された専用の本番通常ブラウザで、実作品ではないテスト用編み図を使う。自動テスト除外やオプトアウトを恒久的に解除しない。

1. リアルタイムの「イベント名別のイベント数」で、編集・閾値到達・出力のイベント名を確認し、イベントを開いて利用可能なパラメータを確認する。
2. 詳細なパラメータ確認には、その検証端末だけGoogle Tag Assistantでデバッグモードを有効にする。管理の「データの表示」→「DebugView」で当該デバッグ端末を選び、イベントを開いてパラメータを確認する。DebugViewはデバッグモードなしでは表示されない。
3. 試し描画、閾値到達、未編集出力、同じ状態の再出力、追加編集後の出力、共有取りやめ、別日の初編集を区別する。閾値・日ごとの一度だけの送信と、ID・名前・座標・ハッシュが送られていないことも確認する。端末時計を変える検証は専用環境で行う。
4. 検証後はデバッグを終了し、オプトアウトを設定して再読み込みする。通常レポート・探索は即時ではなく、処理に24〜48時間かかることがある。公開報告は「受信を確認した」等の定性的な記述だけにする。

開発者トラフィックのフィルタを使う場合は適用状態を別途確認する。オプトアウトしたままでは実受信は確認できない。[公式の受信確認](https://support.google.com/analytics/answer/9333790?hl=ja)、[公式のDebugView手順](https://support.google.com/analytics/answer/7201382?hl=ja)

## 運営者の検証操作の除外

本番を通常のブラウザで確認する前に、編集画面のコンソールで実行し、再読み込み完了を待つ。

```js
localStorage.setItem('knitting-editor:analytics-opt-out', '1'); location.reload();
```

このフラグによるオプトアウト時は計測記録も可能な範囲で削除する。Playwright等のwebdriver、`Claude/`を含むアプリ内ブラウザは自動除外される。開発ビルド・iOS版でも送らない。ネットワークでGoogleへの解析通信がないことを確認する。

## 性能と失敗時の扱い

記号ありマス数は`Board.occupiedStitchCount`を差分更新し、描画中に全盤面を走査しない。操作量のビットマップはアクティブな編み図の`rows * cols`バイトだけを確保する。同期ストレージ書き込みはセルごとには行わず、編集後のタイマーで5秒に1回までとし、一度だけのイベント直前、非表示への`visibilitychange`、`pagehide`では即時flushする。したがって即時flushは5秒制限の例外である。盤面ハッシュは初回の基準取得時と出力時に一度ずつ計算する。計測の例外や通信失敗が編集・保存・出力を妨げないことを優先する。
